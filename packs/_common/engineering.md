
# 工程规则

> 所有承担工程工作的角色技能共同遵守本文件；全局约束（总纲、计划制度、工作区纪律与交接说明）
> 见根目录 `CONSTITUTION.md`。本文件与 `CONSTITUTION.md` 是各 `SKILL.md` 的唯一规则来源：
> 两处已说明的内容，`SKILL.md` 不得重复，只做引用与角色特有补充（本角色用什么工具、什么顺序、什么门槛）。
> **内容边界**：本文件只收与具体流程（six-pack、two-pack 等工作流编排）和具体项目都无关的
> 通用工程规则（宪法第三章「踩坑与经验沉淀」）；流程/角色相关经验见各工作流 `SKILL.md`，
> 与具体项目相关的内容只进 `project/handoff.md`，不得沉淀进本文件。
> 与具体语言/工具/框架相关的专项注意事项（问题与解法，随复盘增长）不在本文件，
> 见 `notes/` 目录（`rust.md`、`aps.md`、`mutation-hardening.md` 等，索引见 `packs/INDEX.md`）；
> 交接文件 `project/handoff.md` 的结构与书写规则见 `handoff-rule.md`。

## 工具启动

- **调用契约**：调用任何脚本/CLI 前，先确认其执行契约——运行时/解释器（读首行 shebang）、
  调用方式（直接执行还是经由解释器）、对工作目录与环境变量的要求、前置条件（可执行位、依赖）。
  契约从证据中获取（shebang、`--help`、文档），不从同目录邻位工具或习惯外推——同一目录不承诺同一运行时。
- **路径与工作目录确定性**：命令的实际工作目录可能与预期不符（适配器、子进程、
  重开终端后的新会话都会改变 cwd），相对路径会静默落到非预期位置。凡脚本化调用
  （runner、适配器、工具链脚本）：路径一律使用绝对路径，或在脚本开头显式 `cd` 到约定的根目录；
  对写入落点存疑时先用最小探针确认（打印 `pwd` + 试写 + 回读校验），不要等到收尾才发现产物散落。
- 启动工作前，获取本项目语言所需的每个 CRAP、变异测试（mutation）和 DRY 工具，并使每一个都处于可运行状态。
- 优先使用各工具官方仓库的最新上游版本；在当前环境中能够进行全新安装/构建时，不要依赖过期的缓存副本或 vendored 副本。
- **发行资产形态会随版本漂移**：第三方运行时/工具的 release 资产文件名与压缩格式可能与
  记忆或旧文档不符（格式更换、名称附加标记、文件名不再含版本号等），按旧名直接下载会 404——
  这不代表"没有发布"。先取该版本的资产清单页确认实际文件名与格式，再下载安装；GitHub API
  限流时用 `releases/expanded_assets/<tag>` HTML 页（免认证）读取该 tag 的真实资产清单，
  按 `releases/download/<tag>/<实际文件名>` 直链下载。
- **受限项规则**：若环境中已有对应工具则直接使用；否则按原仓库说明安装；无法安装时**不要中断工作**，在 `project/handoff.md` 的受限项中明确记录"工具 X 不可用"及受影响检查。
- 语言工具表（供参考）：
  - Go：`go install` 安装；变异测试 `github.com/unclebob/mutate4go`，CRAP `github.com/unclebob/crap4go`，DRY `github.com/unclebob/dry4go`。
  - Clojure：Clojure CLI/deps.edn 安装；变异测试 `github.com/unclebob/clj-mutate`，CRAP `github.com/unclebob/crap4clj`，DRY `github.com/unclebob/dry4clj`。
  - Java：Maven（`mvn`）安装；变异测试 `github.com/unclebob/mutate4java`，CRAP `github.com/unclebob/crap4java`，DRY `github.com/unclebob/dry4java`。
- **工具安装位置**：clone/构建后的工具仓库统一放在 `swarm/.tools/<仓库名>/`（工具缓存，跨会话复用；不进归档包、不随会话清除）。会话缓存不随工作区流转：每会话先确认所需工具在位，缺则按上文重建，安装位置与选型理由写入 `project/handoff.md`。APS 仓库名为 `Acceptance-Pipeline-Specification`。
- **上游钉死路径的兼容桥接**：上游脚本/文档钉死的工具路径（如对 `.tools/bin/bb` 的
  硬编码）与实际安装位置不一致时，优先在钉死位置补**符号链接**桥接到真实位置，不要改
  上游脚本——上游脚本属字节级基线与验收契约的一部分，改动会破坏 diff 基线与下游复现；
  链接事实（源 → 目标）写入 `project/handoff.md` 交接。

## 语言默认项

- 对 Clojure 项目，尽可能优先使用 Babashka。
- 对 Clojure 或 Babashka 项目，编写 Speclj 规格测试，而不是 `clojure.test`。
- 如果 Speclj 规格文件发生了变更，先做规格结构检查，再运行测试。
- 对 Java 项目，避免使用 Maven 运行测试；构建专用的测试运行器并改用它们运行测试。

## 设计与可测试性

- 以小的、可评审的增量开展工作。
- 优先选择能支持当前行为、并为下一步留出明确选项的最简单设计。
- 让测试紧贴被修改的行为。
- 将可测试模块与不适合测试环境的模块分离开——后者在自动化测试下会打开 GUI、依赖外部设备、抛出环境错误、发出系统错误或挂起。最大化可测试代码，并将不适合测试的边界降到最小。
- 只有可测试模块才应参与运行测试的工具，包括单元测试、验收测试、覆盖率、变异测试、CRAP 分析、会调用测试的 DRY 分析以及属性测试。
- 将属性测试与常规验证分开。除非该角色负责属性测试验证或用户明确要求属性测试，否则不要在常规单元覆盖率、Gherkin 验收变异、语言变异工具、CRAP 或覆盖率命令中包含属性测试标签。
- **把书面架构规则编码为 grep 级检查时，每条规则的扫描域必须与条款判例的精确违规形态对齐**：「低层不得构造高层类型」只扫低层目录——外层/展示层（及其测试夹具）直接构建领域对象是合规形态，扩面扫描必误报；误报压力会诱使放宽真规则。每条规则注明依据条款、适用目录与已知豁免形态；零发现结论先做阳性对照（临时注入违规行确认脚本变红）再采信。
  **探针形态必须命中规则的扫描域**：只认代码行的规则（如锚定 `^use …` 的模式）对注释形态探针免疫——用 `// use tokio…` 注释做阳性对照会静默通过，据此得出的「零发现」是假阴性而非规则失效；探针必须是规则本要捕获的真实代码行。
- **异步系统的"等待态可见信息"需要在入队时预取**：队列中/等待中的实体若要在 UI 显示总大小、
  进度等元信息（如 HTTP Content-Length），元数据必须在 add 入队时异步预取，不能等开始下载才取——
  否则等待态无信息可显示；预取必须与降级路径成对设计（失败静默、正式工作时再取），且不阻塞
  add 主路径。
- **同名规则路由表与守卫臂必须同步，并用契约单测锁死**：first-match 分派 + 名称表拆组（巨型
  match 为编译护栏拆成多个函数）的结构里，规则名误登记到旧组会使新组带守卫的消歧臂变成死代码
  （同文步骤永远落到先匹配的无守卫臂，另一语义从未被验证且不报错）。凡同名步骤多义分派
  （靠上下文变量守卫选臂），必须配一个静态契约单测：断言规则序（谁先匹配）、规则名只落在
  预期分组、分组不含旧臂——改名/拆组时该测试即红。
- **回退/兜底分支必须与主路径共用同一安全收口**：防护原语（单实例锁、权限收紧、原子写、
  校验）若只在主路径生效，回退分支（无主目录、首选路径失败等退化环境）会静默失去防护——
  表象是"防护正常但换个环境就失效"。把原语流程收口到一个函数（如「打开 + 上锁」），
  回退分支只注入不同的落点参数（目录/路径），不复制流程；回退决策点抽成纯函数单独单测
  （回退环境本身往往不可在测试中安全模拟，如清空 HOME 会与并行测试竞态）。
- **「生成默认文件」类功能的三条纪律**（默认配置模板、样例工程文件等）：① 内容必须从
  产品内既有默认值/常量的单一事实来源拼装，不写第二份字面量（改默认值时模板自动跟随）；
  ② 必须附**往返契约测试**——生成物整体喂给产品自己的解析器，断言得到默认语义
  （防"模板与解析口径漂移"，模板写错键名/值形态时即红）；③「已存在不覆写」用
  create-new 语义原语而非"先 exists 检查再写"（后者有 TOCTOU 竞态，且竞态输家会覆盖
  并发写入者；create-new 把竞态映射为错误，按业务语义折算为成功跳过即可）。
  ④ **操作者钦定权威文本时改用整文本逐字节锁定，并先做钦定值 ↔ 产品常量逐项比对**：
  生成物内容被操作者以完整文本钦定为唯一权威（要求逐字节一致）时，契约测试从「逐行
  contains / 关键行存在」改为**整文本精确比对**（生成输出 ≡ 钦定原文，含空行、行序与
  EOF 收尾字节）——逐行 contains 锁不住字节：多余行、缺失行、空行增删、行尾空白都会
  溜过去，且"每行都在"不等于"只该有的行都在"；钦定文本在此取代「从默认值拼装」成为
  第一事实来源（拼装法 ① 退位），漂移风险转移到"钦定文本 ↔ 产品常量"两处事实来源，
  故钦定落地时必须把文本中的示例值与产品常量逐一比对并登记结果：一致则无事，不一致
  以钦定文本为准、把常量对齐列为实现任务（操作者权威优先），且此比对要在规格层完成、
  不留到实现后被测试撞出。
- **完成类事件的标志字段是 spec 快照，完成判定以权威模型当前值为准**：异步引擎
  在任务启动时构建 spec 快照并随完成事件回传标志（如 has_checksum）——运行中
  热调（Reconfigure）若不携带该字段，快照即过期：按快照标志做完成判定会以空
  期望值产生假性失败、或跳过运行中新设的判定。完成类决策读权威模型当前值；
  引擎按快照执行的物理收尾（改名/清副作用）被快照跳过时，由判定方按幂等原语
  补齐（存在才改名、副作用清理可重入）。

## 提问与确认交互（chat 选择题面板）

> Inversion 访谈、产物确认等一切需要操作者作答的场合共用本协议；specifier 的 Inversion
> 模式按此执行，其他角色在关键决策点（方案取舍、放行确认）征询操作者时同样适用。

- **选择题优先，不用问答题**：向操作者提问一律写成选择题——每题给出一组互斥的候选项
  （覆盖典型答案的 2–5 个选项），并始终附"其他/以上都不是（请补充说明）"兜底项，防止
  真实答案落在预设之外时被强行二选一。
- **用 chat 选择题面板呈现，不用纯文本**：在支持交互组件的 chat 中，使用 chat 选择题面板
  （可点选的选项组件）逐题展示，操作者点选即作答；不要把问题写成大段纯文本或让操作者
  手打开放式回答。按阶段分批出题，本阶段全部作答后再出下一阶段。
- **追问同构**：作答后仍有歧义时，把歧义点拆成新的选择题继续以 chat 选择题面板追问，直到信息收齐；
  连续追问仍收不齐时用兜底项请操作者文字补充，并把未决项写入 `project/handoff.md`。
- **受限退化（chat 输入选择题答案）**：当前通道不支持 chat 选择题面板或异步会话无法逐题等待时，
  退化为让操作者在 chat 中直接输入选择题答案——把选择题写成带选项的编号清单（每题标注
  选项编号），操作者以一条 chat 消息回复答案（如 `1B 2A 3D` 或逐题 `1: B`），兜底项仍可
  文字补充；明确声明"受限项：chat 选择题面板不可用，已退化为 chat 输入答案"并记录
  `project/handoff.md`；答案未到前不得凭假设推进（与宪法第三章「通用失败条件」的 blocked
  规则一致）。
- **端点语义在规格期对齐，不留到实现后被追问**：涉及监听/连接类设计（IPC 传输、服务端口、
  socket 形态）时，向操作者呈现"端点语义卡"四要素——寻址形态（TCP 端口号 / Unix socket 路径 /
  命名管道名）、可达范围（仅本机 / 局域网 / 远程）、可配置性（配置项、环境变量覆盖、默认值）、
  平台支持矩阵。"Unix socket 没有端口号"这类与直觉相悖的事实必须在规格确认阶段讲明；否则实现
  完成后仍会被"监听的是哪个端口/远程能不能访问/端口可配置吗"连环追问，甚至推翻选型返工。

## 验收流水线（APS）

- 使用 github.com/unclebob/Acceptance-Pipeline-Specification 来进行 Gherkin 验收测试。
- APS 提供 `gherkin-parser`、`gherkin-ir-dry-checker` 和 `gherkin-mutator` 三个工具。
- **调用约定（重要）**：Babashka 版 APS 工具是 **APS 工具仓库自己 `bb.edn` 里的 bb 任务**，产品项目的 `bb.edn` 中没有这些任务——在项目目录里直接运行 `bb gherkin-parser …` / `bb gherkin-ir-dry-checker …` 会报 "No such task"，这不是命令语法问题，不要据此改写命令或绕开工具。bb 任务只按当前工作目录下的 `bb.edn` 解析，不支持指定其他项目目录，因此**必须进入工具仓库目录后调用**：
  - 推荐用子 shell 调用（不改变当前 cwd）：`(cd <swarm>/.tools/Acceptance-Pipeline-Specification && bb <任务名> <参数…>)`
  - 或先 `cd <swarm>/.tools/Acceptance-Pipeline-Specification` 再 `bb <任务名> <参数…>`，完成后返回原目录（feature/输入/输出一律用绝对路径，不受 cwd 影响）
- 双参数形式（输入与输出两个参数）：
  - `gherkin-parser <feature> <out>/<stem>.json`
  - `gherkin-ir-dry-checker <ir> <out>/<stem>.dry.json`
- 路径一律使用绝对路径（或相对 swarm 根目录的路径）；中间 IR/JSON 输出统一写入 `.work/tmp/`，不要写 `./tmp/` 或 `/tmp`。
- 对 APS 相关命令，优先使用 Babashka 版工具；仅当其在当前项目环境中无法工作时，才使用基于 Go 的版本（Go 版为独立二进制，按其仓库说明构建后直接调用，不 bb）。
- 项目特定的验收流水线组件包括：验收入口生成器、验收运行时、项目步骤处理器、运行器适配器以及便捷脚本。
- Gherkin 验收变异是指运行 `gherkin-mutator` 对 Gherkin 示例值进行变异；运行必须定期报告进度/状态，以便区分正常长时间运行与挂起。

## 验证

- **验证一律前台运行，不用后台进程**：所有验证（编译、测试、lint、覆盖率、变异、验收）一律前台执行；长耗时的等待方式用"输出 tee 落盘 + 周期 tail 轮询"控制。沙箱回收机制、超时处置与拆块细则见「测试执行纪律」；轮询中断的恢复协议见「长任务的状态与续做」。
- **长验证输出只纯落盘重定向，禁用管道下游消费器**：`cmd > log 2>&1` 后事后 `tail` 查看是唯一安全形态；`cmd | tee log | head` 这类管道链中，下游消费器（head/grep -q 等）提前退出会级联 SIGPIPE/EPIPE 杀死上游（tee 死后写入方随死；Rust 程序 std 忽略 SIGPIPE 但 `print!` 遇 EPIPE 会 panic）——表现即长验证「跑一半无声消失、日志无 summary 尾行」。与沙箱后台回收是两种不同根因，均以「日志有无 summary + 残留进程表」区分归因。
- **失败先归因，再重试**：命令报错先按错误形态归类，针对类别处置，不换着参数盲试；
  修复后用无副作用的最小探针（help/list/status）验证调用方式，再进正式流程。常见类别：

  | 失败类别 | 典型信号 | 正确动作 |
  |---|---|---|
  | 运行时不匹配 | 语法错误出现在"不该出现的位置"（如 bash 报 Python 的 import 语法错） | 换正确解释器，而非改参数 |
  | 权限缺失 | Permission denied | 补可执行位或显式指定解释器 |
  | 路径/文件不存在 | No such file or directory | 核对相对路径与当前工作目录 |
  | 用法/参数错误 | usage / help 提示 | 查 `--help` 与官方文档 |
  | 环境缺失 | command not found / 缺依赖 | 安装依赖，或按受限项规则如实记录后绕行 |
- **"静默空输出"先怀疑过滤参数的默认值，再下"没有问题/没有重复"的结论**：多语言工具的默认
  作用域常与直觉不符（如 PMD CPD 不带 `-l rust` 时默认只收 java、静默报 "No files to analyze"），
  工具成功退出 + 零输出可能是过滤参数把目标全滤掉了，而不是目标本身干净。凡"零发现"结论，
  先用一个人工已知存在问题的最小输入做阳性对照，确认过滤参数真的生效，再采信空结果。
- **分组/配对类报告的发现清单不是全量清单，"几处"以独立计数为准**：重复检测、冲突检测等
  工具常把同一问题归并为一个发现条目（tile/分组），条目内只列部分代表性位置——按报告条数
  数出来的"2 处重复"实际可能是 16 份拷贝。据此排工作的优先级会系统性低估；采信前用独立
  手段（grep 计数、逐文件核对）确认条目数与真实实例数的对应关系。
- **对照基线与实验同语境**：任何"与基线对比"的验证，基线必须在与实验完全相同的
  并发配置、环境变量与工作目录语境下取得（工具会向 worker 注入环境时，手跑基线也要带全）；
  语境不一致的对照是无效对照。度量结果反直觉时，先怀疑度量工具本身（路径假设、语境、版本、身份），
  复现一次后再采信。
- **度量口径与上游可比**：后续角色做覆盖率 / CRAP / DRY 等度量时，工具与开关尽量沿用
  上游交接说明（`project/handoff.md`）声明的口径（上游用什么工具产出基线数字，就沿用同
  工具同开关），数字才可与上游基线直接对比；口径必须变化时在 `project/handoff.md` 写明
  差异与影响。选型时一并确认工具的输入格式对接点（如 CRAP 工具以哪种覆盖率报告为输入），
  缺输入先产出输入再运行工具。
- **受限口径的近似度量**：目标语言缺失标准工具（如无任何公认 CRAP 工具）或既有工具与当前工具链
  不兼容（编译失败）时，按"标准公式 + 既有标准工具的输出"做受限近似（如以行覆盖率与分支计数
  代入 CRAP 公式 comp²(1-cov)³+comp 估算）；近似口径、偏差方向与影响范围写入 `project/handoff.md`，
  近似值不得冒充标准工具输出，「护栏」的不自制替代工具规则依然适用。
- **计划的估计数字与实测不符时，以实测为准并记录偏差**：计划/规格中的数量口径（场景数、
  执行次数、用例数）是估计值，实测多 1 少 1 属常态；不硬凑数字、不回改已成文计划，把实测值与
  偏差原因写入 `project/handoff.md`，下游拿到的必须是真实口径。交接的总账数字必须能从列出的
  分项明细复算自洽，未实跑的规模不得混入已验证口径。
- 在运行语言、构建或测试命令之前，优先使用项目本地缓存/配置路径。避免使用会把内容写到项目之外、并可能触发沙箱或权限限制的默认缓存位置。
- 验证工具一次只运行一个。不要并发运行 CRAP、DRY、覆盖率、语言变异、Gherkin 变异或结构检查。
- 工具接受 worker 数量/并行度限制时使用多 worker（worker 数量与 worker 上限数均设为当前运行机器的 CPU 核心数）。具体选项名因工具而异，先查该工具的帮助确认；工具不提供并发选项时顺序执行并在 `project/handoff.md` 记录受限说明，不是违规。变异加固需要并发而工具不支持时，可按 `packs/_common/notes/mutation-hardening.md` 的 worker 副本隔离自建进程级并行。
- 函数变异是基于源码清单（source manifest）的差分变异。不要传入 `--mutate-all`。
- Gherkin 变异是基于 feature 清单的差分变异（`--level hard`）。不要传入 `--level full`。
- 验收测试生成与验收测试运行必须按顺序执行；避免在生成验收测试的同时并发运行全量语言测试命令。
- 只要项目存在相关的本地验证命令，就在声明完成之前运行它。
- **最终验证序列**照常执行；环境缺少某工具时按"工具启动"的受限项规则记录，并在 `project/handoff.md` 中明确剩余风险。

## 测试执行纪律

- **测试与验证一律前台运行并显式设超时，不用后台进程**：
  - 沙箱会在发起命令的**工具调用正常结束**时回收该调用派生的整个后台进程组——不等新消息、
    不等超时、无报错；`&`/`nohup`/`setsid`/`disown`（乃至后台驱动脚本）全部无效
    （回收对象是进程组而非终端会话，挡 SIGHUP 与摘作业表都不相关）。**前台纪律没有例外。**
  - 后台跑测试看不到实时输出、失败时留孤儿进程、会话"是否卡死"无从判断；被回收的表象不是
    失败本身，而是"输出截断/进程蒸发/结果悬空"。判别：调用返回后进程消失 + **日志 0 行/0 字节**
    （文件壳已建、内容永不到来）＝ 后台回收，属环境性问题，原样重跑无益；日志**有内容**但有
    FAIL ＝ 真实测试失败，走「验证」一节的失败归因流程——两者不可混淆。
  - 超时到点仍未结束：先中断，检查有无错误（部分输出、日志、残留进程）；无错误且工作量确属合理
    则延长超时重跑；超时需反复延长时按挂起（hang）排查根因，不要无限加时。中断后复跑前先清理
    残留（进程、锁、临时文件），确认无残留再测，清理次序见下条。
  - 长耗时任务用"输出 `tee` 落盘日志 + 周期 tail 轮询"等待（轮询中断的恢复协议见
    「长任务的状态与续做」），不做阻塞式单调用；能拆块则按 feature/分组拆成短块
    （单块暴露窗口最小化，中断只补跑一块），单块时长严格控制在单次工具调用超时内，块间彻底
    清理、按块独立日志断点续跑（日志尾部 `== summary ==` 判块完整性，续跑只补缺块）；确需跨
    调用存活的常驻服务（如冒烟验收的 daemon）在同一调用内"拉起 → 使用 → pkill"一条龙完成，
    不留到调用外。
- **交互会话中长测试会被新消息取消，用"预告 + 落盘日志 + 增量重跑"止损**：交互通道里前台长命令
  （全量测试、全量构建）随时可能被操作者新消息打断（工具调用报 context canceled）——这不是测试
  失败，不要误诊。缓解三件套：开跑前向操作者预告预计时长请其勿插话；输出 `tee` 到落盘日志
  （中断不丢已完成部分，失败详情可事后翻阅）；依赖增量编译/缓存使重跑成本远低于首次。
  不因此改用无人值守的后台进程——被打断就带着日志从断点续跑。
- **清残留的次序是"先杀进程、再删状态"，删目录杀不掉进程**：中断/超时后复跑，若只删运行时
  状态目录（socket 文件、锁、数据库目录）而不先杀持有它们的进程，会得到双重假 FAIL：老进程
  仍持有已删 socket 的 inode，新连接全部落空；新实例拉起时又撞"已在运行"单例守卫直接退出。
  守护化/双 fork 的服务被 timeout 杀掉前台启动器时 worker 仍存活（继续占端口、持 socket），
  所以清理必须按**进程名**（服务自己的守护进程名，而非启动器命令行）逐一 pkill，`pgrep`
  确认无残留后，再删状态目录与临时文件——次序反了等于没清。
- **以 pid 命名的测试临时目录跨会话可复用，基线"神秘污染"先查陈旧残留**：夹具用
  `std::process::id()`（或等价的进程标识）作临时目录后缀时，pid 跨会话会复用——先前
  会话的同名目录（含落盘的 registry/状态文件）被本轮同名测试整体继承，表象是「跨测试
  互相污染」式假失败（开局恢复出幻影实体、计数多 1、"断言空表非空"），单独重跑该测试
  又无法复现（新 pid 目录干净）。归因线索：失败断言的是"开局即应有的干净态"，且临时
  目录下有大量历史 pid 后缀的残留。处置：基线复跑前先清理本项目的临时目录前缀；「开局
  干净态」是 fixture 自足纪律（见「fixture 步骤自足」条）的环境维度延伸。
  **「pid + 时间戳」双后缀在同进程并发测试下仍会撞**：时间戳粒度（毫秒）内多次夹具
  调用得到同一目录名，先完成测试的 `remove_dir_all` 会删掉并发测试正使用的工作目录，
  表象是偶发 NotFound/ENOENT 类假失败（覆盖率工具插桩拖慢测试时更易触发）。时间戳
  只防跨会话、不防同进程同粒度并发；夹具唯一性要加**进程内原子自增序号**参与命名
  （pid + seq + 时间戳），使每次调用唯一。排查时按"同前缀目录名是否可能由两次并发
  夹具调用生成"审查，不只看跨会话残留。
  **根治靠收口，不靠各处自查**：分散式「每个测试模块自写一套命名公式」会让同类缺陷
  随新模块复发——把唯一化命名收敛为单一 cfg(test) 工具函数（放在所有测试 crate 都能
  引用到的位置，如最内层公共模块），新增夹具一律经它构造，全仓不再出现手拼
  `join(format!(...pid...))`。审计优先级按「该路径是否被夹具构造函数读取以恢复状态」
  排：恢复类路径（构造时读入残留状态文件）的污染直接改变被测行为，纯写读类只是卫生
  问题；同时把项目历史上易复用的既有唯一化方案并入该 helper，而非平行保留两套。
- **分块验收的"块首竞态"是假 FAIL 高发位**：每块第一个场景的连接/请求可能早于被测服务就绪
  （socket 文件尚未落盘），表象是块首单点 FAIL 而其余全绿。判别三证据：仅块首 FAIL、原样复跑
  即过、该 feature 单独重跑全绿——三证齐即判假 FAIL 并修正结果，不追产品根因。
  缓解：按上一条彻底清理 + 拆短块；根治可给验收 runner 加块首连接预热重试守卫（基建可选优化）。
- **先确认运行器的输出契约，再解读结果**：不同 runner 输出协议不同——有的逐项打印，有的
  只在失败时打印（如"静默输出 + exit 0 = 全部通过，仅打印 [FAIL …] 行"）。空输出不等于
  异常；按契约解读，不按预期猜测，必要时读 runner 源码确认。
- **分发表首匹配时，泛化正则会遮蔽专有形态**：按注册顺序取首个匹配的处理器/路由/规则表
  （测试步骤分发、URL 路由、lint 规则等皆属此类）中，先注册的泛化正则（尤其带可选组
  `(?: …)?`）会吞掉后注册的专有形态，使专有处理器"永不执行"，表象是下游断言失败或卡死。
  专有形态必须用 tempered 正则排除泛化后缀（如 `((?:(?! 分隔符).)+)`），并删除为绕过而打的
  特判补丁——补丁治标，分发根因不除会换个场景再犯。
- **数据驱动场景禁止硬编码具体行的实体名**：Examples 多行/参数化场景中，后续步骤要用到
  本轮行产生的实体（任务名、链接、文件名）时，由产生它的步骤显式写入运行时上下文，按上下文
  查找；硬编码首行的名字在换行后必然落空（查无实体误报或空指针）。
- **种子状态必须避开被测系统的后台自动化**：被测系统带队列/调度/重试等自动推进逻辑时，
  测试种子不要用会被自动推进的状态（如"等待中"会被队列自动启动并秒级完成），改用自动化
  不触碰的状态（如"暂停"），给批量操作留确定起点——否则 fixture 与测试竞态，出现
  "操作时已不在预期状态"的假失败。
- **无退出条件的线程绝不 join**：测试内自建的 mock server/常驻线程若阻塞在无限循环上（如无限
  accept/消费循环），join 它等于永久挂起——测试看似在跑，实为死等，覆盖率等工具也会被连带挂死。
  要么显式 detach（测试进程退出自然回收），要么给线程实现 shutdown 契约（哨兵连接、关闭监听、
  退出通道）再 join；多个测试共享同一 mock 基建时，把安全策略（一律 detach）统一收口在共享模块。
- **夹具函数不得吞掉控制通道的发送端**：把「命令/控制通道的发送端」封闭在测试夹具函数内部
  （夹具只返回接收端）时，发送端随夹具返回即 drop，被测系统的「通道已关闭」分支会在第一个
  select/轮询立即触发（recv 得 None ≈ 对端消亡），表象是"早事件到了、终态事件永不到"的全量
  超时假失败。处置：keep-alive 句柄（发送端）必须作为夹具返回值交调用方持有至断言结束；
  归因探针：probe 类早事件正常到达 + 完成类事件按 deadline 缺失 + 单测隔离复现，即查通道
  生命周期。
- **操作型测试断言"隐式副作用后的最终状态"**：有状态系统的操作自带隐式自动化（删除自动补位
  队首、完成自动触发收尾、超时自动重试）。测试某操作时若系统已自动完成后续行为，再手动补做
  该行为必然断言失败（重复执行或状态已漂移）——先枚举被测操作的副作用清单，断言副作用后的
  最终状态，不要手工复演系统已自动完成的事。
- **断言前先归一化口径**：规格/文档用语与实现标签可能对同一状态用词不同（分组语言
  "正在下载" vs 列表行标签"下载中"），比较前先做归一化映射，不要逐字断言。
- **用例间注入配置会残留，场景开始先复位基线**：长测试块里"调短注入"类配置键（超时、
  限速、阈值）会跨场景残留并改变后续场景路径——每个依赖注入配置的场景开始时显式写入
  合法基线配置并触发生效（reload），不要假设上一场景的注入已被还原。**"写入成功 ≠
  生效成功"**：值低于校验下限的写入会被整体拒绝（磁盘已改、内存回滚），后续 reload
  全部静默失效——注入值必须先核对校验下限；"未配置"的复位一律用官方未配置形态
  （如 null），不用看似等价的零值。
- **同一 env 键只归一个测试触碰，双分支合并为顺序相位**：测试二进制内并行测试共用进程
  环境，两个测试分别 `set_var`/`remove_var` 同一键会互踩（读到的值取决于调度时序），
  表现为偶发失败。一个环境变量键只允许一个测试触碰；需要覆盖"设置/未设置"两条分支时，
  合并为**一个测试内的两个顺序相位**（先设值断全路径、清理后断静默路径），不拆成两个
  并行测试。
- **正/负探测的加固方向相反**：异步完成类行为（先应答后重绑、先建新后退役）的**正向
  探测**（新端点就绪/资源出现）要加有界重试窗（间隔轮询至短超时），否则负载抖动即假
  FAIL；**负向探测**（旧端口已关/资源已释放）保持单发——对"已释放"重试只会稀释断言。
  两者不可套用同一模板。
- **"门控 Given、武装 When"驱动异步状态推进**：被测行为依赖异步推进（元数据获取、
  后台确认）时，fixture 先以"门控"资源让系统停在稳定等待态（Given 可复现），再由
  When 步骤放行/武装资源，让状态推进发生在确定的观察窗口内——不要用不可控的真实
  时序或超长固定等待。
- **门控资源要中性应答，不能挂起**：门控式依赖（tracker/服务端）在未武装阶段的
  应答形态有讲究——挂起（不响应）会把依赖方推进其超时失败路径（重试耗尽、任务转
  failed、状态机歧路），污染后续断言与恢复口径；应答应中性化（空集/零 peer/空列表），
  让被测系统停留在稳定的"无进展等待"态，武装后再供真实资源。选用现成 fixture 时
  先核对其未武装分支的应答形态，不要只看"门控"标签。
- **探针/fixture 的会话与资源会跨场景残留，断言用包含口径**：探测类客户端 attach 建立
  的会话、fixture 注入的任务在跨块回归中是合法残留状态——"列出 X"类断言一律用
  "包含目标条目"口径，勿用排他 `len==N`；跨场景计数类断言的基线必须取在自身 fixture
  创建之后。
- **场景结束恢复受控状态**：会污染后续场景的副作用（写入黑名单/配置的条目、一次性
  会话、判重键）在场景收尾时移除或恢复；fixture 标识注入唯一化（随机后缀/唯一 query）
  避免跨 run 判重与避让；断言读实际生效配置而非硬编码默认值（验收注入值会改变被测
  行为路径）。
- **fixture 步骤自足**：写配置/建目录类 fixture 步骤必须自足（补父目录创建等），
  不假设 Background 或前置场景已建好环境——Background 被动步骤（刻意不拉起服务）
  是合法设计，首场景不能依赖其副作用。
- **盘上状态预写必须战胜利后台写入者，且退出路径要选对信号**：fixture 直接在盘上
  预写持久化状态（控制文件/快照/缓存）时，存在三类覆盖者：① 异步引擎的停止收尾
  ——IPC 可见的状态翻转 ≠ 收尾完成（驱动在下一个事件边界才观察到 stop 并做最终
  保存），周期 saver 在驱动退出前也会以内存态覆写；② 其他场景/实例的退出钩子——
  TERM 优雅退出若携带 flush-all 类钩子，会在 restart 期间以内存态覆盖预写；③ 并发
  场景残留。处置三件套：预写后做**稳定窗校验**（采样间隔 × 次数 > 最快覆写者周期，
  被覆盖则重写直至连续无变化，不得用固定盲等）；异常终止语义的场景用 **SIGKILL 直杀**
  （无优雅退出 → 无钩子刷盘，且与被测语义一致）；预写内容与磁盘上真实进度强无关时
  断言只锚定预写值。
- **fixture 的自动推进竞速：被测操作（stop）可能落在状态机歧路后**：loopback 下
  下载瞬时完成的 fixture 与操作时序竞速——任务先转做种，同一操作词按状态机走到不同
  终态（stop 做种 → completed，stop 下载 → paused），且完成路径与状态翻转存在跨线程
  覆写窗口。处置：fixture 侧用中性依赖（空 peer 列表）钉住稳定中间态，操作落定后再
  武装资源（配合上一条与门控条款），不要事后加长等待硬扛竞速。
- **网络 fixture 的 accept 循环遇错 continue**：服务型 fixture 在 accept 返回错误时
  break 会因一次瞬时错误永久失去服务能力（后续连接全挂）；应记录并 continue。
  断言"对端关闭连接"时，本端多写的未读残留字节会把干净 EOF 变成 ECONNRESET——
  探针要么恰好在协议边界停笔（只写协议要求的字节），要么显式把 ConnectionReset
  分类为"对端已拆连"。
- **校验器对夹具数据的容差必须有显式边界并落盘记录**：夹具数据不完全符合标准格式
  时，放宽校验是决策不是妥协——放宽依据、边界值与理由写入 `project/handoff.md`，
  不静默硬编码、不改夹具迁就实现。
- **度量工具的符号级输出不可直接精确匹配**：编译器会把泛型实例化、闭包、内联生成为同名或内部
  改名的符号（同名泛型互相覆盖、闭包实例噪音），按符号名逐个对账脆弱易错。跨语言通则：覆盖率等
  度量优先采信 summary 与行级数据；确需函数级归并时按（文件, 规范化名）聚合取极值，并过滤
  编译器内部命名约定的符号；解析器宁薄勿厚，降维比精确更可靠。
- **工具的过滤参数要验证生效阶段，不生效就双层过滤**：同一工具的不同过滤开关作用于不同阶段
  （构建插桩/数据采集/报告生成），"加了过滤参数"不等于"已生效"——先用一次最小输出验证过滤
  结果；不生效时改用"构建期排除 + 解析期跳过"双层过滤，不纠缠单个开关。
- **测试数据规模遵循操作者要求，大体积 fixture 用稀疏文件**：测试文件最大值**默认 100M**，
  除非操作员明确提示修改该值，不得自行加码或改用更大默认；需要大文件时用稀疏文件
  （`set_len`/`truncate`/`fallocate`）构造，磁盘开销可忽略而语义不变。
- **交付前清理构建缓存**：打包/交付前清理 `target/`、`node_modules/` 等构建缓存与会话临时
  目录——体积大、可重建、不属于产物；产物只含源码与必要交付物。**压缩包体积异常巨大，几乎
  必然混入了构建缓存**——交付前看一眼包体积是零成本的体检。`bin/swarm complete` 已把清理
  做成打包前自动步骤；角色在会话内交付任何压缩物时同样适用本条款。
- **not_in 子串断言的区域必须与规格语义面板对齐（面板箱体截取）**：伪终端断言里
  「画面不应出现 X」若作用于整列/整屏切片，会命中其他面板的合法常驻文本（如图表
  面板标题含「速度」而规格只约束详情面板无速度行）——文本区域按面板箱体截取
  （目标面板标题行起、相邻面板标题行止）；切片列位以实测列位为准并落盘，不沿用
  历史布局注释；区域口径收口在共享助手内（跨套件复用一处修正）。
- **列表行右缘渲染的数值（进度/百分比）落在多面板分界列附近，面板切片读不全**：
  右栏切片的起始列可能吃掉列表行右缘数值的头几位，截断片段仍可能被宽泛正则命中
  （如「21.0%」被列切片读成「1.0%」）——此类数值一律读全宽行并以选中光标标记
  定位目标行，先整行匹配再考虑区域裁剪；零命中结论先怀疑列切片截断。
- **单一 toast/状态槽位的产品：瞬时提示按「后发覆盖先发」处理**——同刻多次
  set_toast 只有最后一次可见：①关键提醒（错误/回退口径）必须最后发出，常规
  确认提示先行；②端到端断言锚定瞬时提示时，用门控（慢速任务）拉长提示存续窗，
  防止快速完成路径的后续提示把被测提示顶出观察窗；③同刻双提示且两者都需可见
  属规格问题，报操作者裁决（合并文案或双槽位）。

## 长任务的状态与续做

- **落盘状态是唯一可信状态源**：长会话/多代理协作中，对话历史可能被压缩、截断或丢失（子代理
  返回结果、早前结论都可能在其中）；工作是否完成以落盘证据为准——计划文件勾选、
  `project/handoff.md`、代码库与测试的实测结果，而不是对话记忆。
- **恢复工作时先核对、再续做**：接手中断的任务，先用最小验证命令核对代码库实际状态（测试数、
  文件存在性、工具在位性），与计划文件勾选互相印证后再决定从哪一步续做；记录与实测不符时，
  以实测为准修正记录。
- **长测试的轮询等待与轮询中断恢复协议**：真实耗时的慢场景测试（限速低速用例、真实等待类验收）
  用"输出 tee 落盘日志 + 周期 tail 轮询（盯进度与 FAIL 计数）"等待，不做阻塞式单调用、不转后台。
  轮询本身被会话中断时，恢复动作有固定次序：先查进程是否存活（`pgrep -af` 类探针），再 tail
  落盘日志核对进度与已完成的场景段——进程在则继续轮询；进程亡则带着日志从断点重跑并恢复轮询。
  会话中断 ≠ 测试失败，不因中断盲目全量重跑，也不凭"对话里说过跑到哪"推断进度——日志与
  进程探针才是轮询现场的唯一事实来源。
- **每完成一步立即落盘**：计划勾选、notes 增补、日志追加随步进行，不积攒到收尾——中断与压缩
  何时发生不可预知，落盘延迟就是丢失窗口。
- **"已接收未启动"是真实的悬空态**：任务指令进入对话后，若在执行任何动作前被打断（摘要
  请求、上下文压缩、新消息插入），任务处于"已接收、零执行"的悬空态——对话历史里有指令，
  落盘层面无任何痕迹，操作者视角即"卡住了"。恢复时先跑无副作用的状态探针（status/list/
  工作区清点），核对流水线、会话与产物的实际状态，再从断点按序续做；不因"对话里说过"就
  推断某步已完成。
- **开工第一个物理动作是落盘计划**：收到任务后先写计划清单（哪怕只有一行），再开始探查、
  阅读与实现——计划文件是最小恢复锚点，任务越早期被打断，越只有已落盘的计划能证明
  "任务存在、进行到哪"；先落盘、随做随勾，中断恢复才有序可循。
- **中间角色被直启且交接缺失时，以操作者当次指令为任务依据**：非首角色（如 coder）在
  `project/handoff.md` 缺失时被直接启动（此时上游交接来源＝操作者 chat 输入，宪法第一章
  「上游交接双来源」）：不臆造上游意图，也不反向补写
  mission.md（补写是首角色的职责边界）；以操作者当次明确指令为唯一任务依据，把
  "任务来源＝操作者指令、handoff.md 缺失"如实写入 `project/handoff.md` 交接，拿不准的点向操作者
  确认而不是假设。
- **压缩后的对话记忆不可作为引用来源**：上下文被摘要/压缩后，早期工具输出与文件内容的
  细节可能失真或丢失；凡引用文件原文、此前的命令结果或结论，先重新读取落盘文件核实，
  不凭记忆复述——记忆只用于定位线索，事实以落盘原文为准。
- **环境不跨会话持久，恢复会话先重建环境**：会话恢复/新 shell 里 PATH、env 可能全部丢失
  （工具链本体完好，如 `~/.cargo/bin` 仍在但 `cargo` not found）——丢的是注入，不是安装。
  恢复时先按 `project/handoff.md` 记录的安装位置重建环境（`export PATH=…`），再用最小探针
  （`--version` 类命令）确认在位；工具的安装位置、版本、环境注入方式必须随 notes 交接。
  重建是否完整要用强制重做来验证：零改动的增量构建会静默跳过编译/链接阶段，把环境残缺
  （如链接器桥接目录不在 PATH）掩盖到下一次真编译才暴露——`--version` 探针之外，再强制
  重做一个可被缓存跳过的步骤。这是"落盘状态是唯一可信状态源"在环境维度的延伸。
- **沙箱/托管环境会回收父进程已退出的 detached 后台进程**：`nohup`/`setsid`/`disown` 都逃不过
  （实测分钟级探针即被杀），长跑工具只有两条活路：①前台分片——每次调用限时（如 `timeout 575`
  包 `timeout` 而非靠外层杀，进程收 SIGTERM 会做增量落盘），配合工具自身断点续跑机制分片推进；
  ②给工具找一个**存活的托管父进程**（如常驻 mini-service/守护 bun 进程）`spawn` 之——父活则子活，
  会话通过轮询托管方的状态接口监视进度。判别"进程为何死了"先看父进程是否还在：父亡被连坐
  与工具自身崩溃的处置完全不同（前者续跑即可，后者先查日志）。
- **重 scratch 工具开工前先做磁盘预算，盘满会制造假判定**：每并发 worker 一个全量构建树
  （数 GB 级）的工具（变异框架、覆盖率、交叉构建），峰值 ≈ worker 数 × 单树体积；被杀/中断的
  进程会泄漏 scratch 目录（正常退出才清理）。预算前先 `df` + 清点残留 scratch，运行中低于
  阈值即主动终止（看门狗轮询）；磁盘满的典型症状是链接期 `cc failed`/`SIGBUS` 与批量假
  unviable/假失败——凡"整批同因失败"先查盘再信工具。

## 护栏

- 不要自行发明项目本地的 CRAP、DRY、变异或覆盖率替代品。安装并运行标准工具（如 `crap4clj` 配合 cloverage、`dry4clj`、`clj-mutate`、speclj，或语言工具表中所列工具）。不要把自制的 `bb crap` / `bb coverage` / `bb mutation-count` 任务当作这些工具。
- 不要手动编辑变异测试或 Gherkin 验收变异清单；让经批准的变异工具在其正常运行过程中更新这些清单。
- 除非任务需要，否则不要提交无关的本地修改或生成的产物。
- 在依赖一个不熟悉的命令之前，先查看其本地帮助或项目文档。


## 通用工程沉淀（会话复盘追加）

- **带时间窗组件（滑窗/令牌桶/退避计时）的单测基准取组件内部样本**：速率计算用
  「样本两端差值/时间跨度」而不是「样本与当前 Instant::now() 差值」——测试执行有
  毫秒级耗时，以 now() 为右端点会把测试耗时算进速率，断言必然抖动失败。
- **跨 cfg 的导入在 `cargo fix` 后必须复跑全量测试**：fix 以非 test 编译口径判断
  未使用导入，会删除仅测试引用的 `use`（见 notes/rust.md 同款条目的 Rust 细节）。
- **周期兜底持久化要内容幂等，判重收口在持久化原语而非调用点**：定时兜底保存（如每 N 秒
  落盘注册表/状态快照）若不判内容变化，空闲期会以恒定节奏重写字节相同的文件——无谓
  temp+rename、mtime 抖动与 SSD 磨损，且掩盖「写盘 = 有事发生」的观测信号。判重做在
  调用点需穷举全部变更路径，漏一处即脏数据；做在持久化原语内部（序列化结果与盘上现有
  内容字节比较，一致即跳过，文件缺失/损坏照常落盘自愈）则一处收口、全部调用点自动幂等。
  验证用双断言：内容一致时重写不得发生（mtime 不变为证）+ 内容漂移后必须落盘（防过度
  跳过）；mtime 断言两写之间需留数十毫秒间隔以越过文件系统时间戳粒度。

- **重复属性 `#[test]` 会把同一测试注册两次，计数对账要防「虚增」**：Rust 中同一函数
  叠两个 `#[test]`（典型场景：文档注释插在两个属性中间）不报编译错，clippy 仅发
  duplicate_macro_attributes 弱告警，但 rustc 会按属性个数注册同名测试——通过计数
  含重复项，基线被静默虚增。防法：①格式化时保持「文档注释在前、属性紧贴函数」的
  顺序（rustfmt 不整理属性间注释）；②轮次对账除总数外抽验「测试名唯一性」
  （`cargo test -- --list | sort | uniq -d`）；③发现计数莫名 -1/+1 时先查重复注册
  而非删改测试。

- **负载共存型 flaky 的判别法（点位漂移 + 单跑必过）**：与测试并行运行的重量级任务
  （变异批量执行、覆盖率插桩构建、多 worker 重链接）会以资源挤压制造「每轮全量恰好
  偶发 1 个失败、且失败点位每次不同、单跑该测试必过」的模式——这是负载 flaky 的指纹，
  判据三点齐备即核销：①失败点位漂移（非固定同一断言）；②单跑必过（含小批量重跑）；
  ③系统空闲后全量复跑绿。不要把它误判为回归去修测试，也不要当作产品缺陷报告；
  反之，点位固定、单跑必挂才是真问题。预防优于判别：重量级验证与测试分时串行，
  插桩构建下对时序敏感断言预留裕度。

- **度量数字对账先核口径，再比数值**：与历史度量（重复块数、覆盖率、测试计数）对比
  前，先确认统计口径逐字一致——目录范围（如 src-only 与 src+tests 是两套数字）、
  阈值参数、工具版本改参（同一子命令的选项名会在大版本间更名）——否则把口径差
  误读为回归或改进。口径本身要随验证命令一起写进交接，后人按同口径复跑才能对上账；
  历史交接未记口径时，以旧结果文件的内部分布反推（如重复块全部落在 src 下即
  src-only 口径），核实后再对账。

- **批量编辑的"原子性"以落盘核对为准，不凭工具回执**：批量编辑类工具可能声称
  原子应用（全部成功或全部不动），实际却部分落盘（前几笔已写入、后一笔报重复/
  不匹配后中止）——回执说"未执行"不等于盘上没动过。批量编辑后、编译验证前，
  先用最小探针核对实际落盘状态（按编辑意图 grep 目标特征行计数、抽验关键片段），
  与预期笔数逐一对账；对不上先按落盘现状续做（补齐未应用笔、不重复已应用笔），
  不要按回执口径盲改或整批重放（重放会把已落盘的编辑当未执行再打一遍，制造
  重复或覆盖）。这是「落盘状态是唯一可信状态源」在编辑工具维度的延伸。
- **同文件多调用点重复体的去重用"共享实现 + 原地一行委托"**：同一文件内多个
  测试模块/调用点重复同一段实现时，把实现收口到单源（共享模块或父级函数），
  各重复点原地保留一行委托调用（签名与名字不变）——调用点零改动、diff 面最小、
  行为等价由编译器与既有测试锁定；比搬移/改写全部调用点小一个数量级的改动面，
  重复检测（CPD 类）的重复块也随之消失。委托体的 doc 注明单源位置即可。
